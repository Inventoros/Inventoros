# Inventoros REST API

This directory contains the API reference for Inventoros.

- **`openapi.yaml`** — OpenAPI 3.0 specification covering every public REST endpoint.
- **`README.md`** (this file) — narrative overview, auth, rate limits, error envelope, code examples.

The full v1 surface is mounted under `/api/v1`. There is also a separate (auth-required) Sanctum-protected GraphQL endpoint at `POST /graphql` powered by `rebing/graphql-laravel` (see [GraphQL](#graphql) below). This document focuses on the REST API.

A live, interactive Stoplight Elements UI is also available at `/docs/api`, generated by `dedoc/scramble` from the controller doc-blocks. Outside the `local` environment it requires a signed-in user; set `API_DOCS_PUBLIC=true` to publish it. `tests/Feature/Api/OpenApiSpecCoverageTest.php` fails when a `/api/v1` route is missing from `openapi.yaml`.

## Base URL

```
{APP_URL}/api/v1
```

where `APP_URL` matches the `APP_URL` value in your `.env` (e.g. `http://localhost`, `https://inventoros.example.com`).

## Authentication

Inventoros uses [Laravel Sanctum](https://laravel.com/docs/sanctum) personal-access tokens. Every request (except `POST /api/v1/login`) must include:

```
Authorization: Bearer <your-token>
```

### Obtain a token

```bash
curl -X POST "${APP_URL}/api/v1/login" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "email": "you@example.com",
    "password": "your-password",
    "device_name": "my-laptop"
  }'
```

Successful response (`200`):

```json
{
  "message": "Login successful",
  "user": {
    "id": 1,
    "name": "Jane Doe",
    "email": "you@example.com",
    "role": "admin",
    "organization_id": 1
  },
  "token": "1|aBc...XYZ",
  "token_type": "Bearer"
}
```

Store `token` securely. The plain-text value is shown **only once**.

### Token management

| Endpoint                              | Purpose                                            |
| ------------------------------------- | -------------------------------------------------- |
| `POST   /api/v1/login`                | Issue a new token (rate-limited 5/min/IP).         |
| `POST   /api/v1/logout`               | Revoke the current token.                          |
| `GET    /api/v1/user`                 | Get the authenticated user + permissions.          |
| `POST   /api/v1/tokens`               | Create a named token with optional ability scopes. |
| `DELETE /api/v1/tokens/{tokenId}`     | Revoke a specific token by id.                     |

Users can also manage their own tokens in the app under **Settings > API tokens**: list them (name, abilities, last used, created), create one with abilities picked from the permissions they hold (the plaintext is shown once), and revoke them.

## Multi-tenancy

Every record carries an `organization_id` and is scoped to the authenticated user's organization. Cross-organization access returns `404 not_found`, **not** `403`, to avoid leaking the existence of other organizations' resources.

## Permissions

Almost every route is guarded by the `api.permission:` middleware (alias of `App\Http\Middleware\CheckApiPermission`) which checks the authenticated user against one or more permission strings. The middleware accepts `|`-separated permissions and grants access when the user holds **any** of them (the default), e.g.:

```
api.permission:view_products
```

Every permission string is a case of `App\Enums\Permission` (a test fails if a route names anything else), one per verb: for example `view_customers`, `create_customers`, `edit_customers`, `delete_customers`, `approve_orders`, `manage_returns`, `transfer_stock`, `create_stock_audits`, `manage_stock_audits`, `view_users`, `create_users`, `edit_users`, `manage_organization` (webhooks). The OpenAPI spec lists the permission for each route.

When a token was created with a list of abilities, the token must also include the permission, so a scoped token can never exceed its abilities even when its user holds more. Tokens without abilities or with `*` fall back to the user's permissions.

A request lacking the required permission returns `403 forbidden`.

## Rate limiting

| Scope                      | Limit             | Keyed by             | Defined in                                  |
| -------------------------- | ----------------- | -------------------- | ------------------------------------------- |
| Entire `/api/v1/*` group   | **60 req/min**    | user id (or IP)      | `App\Providers\AppServiceProvider::boot()`  |
| `POST /graphql`            | **60 req/min**    | user id (or IP)      | same `api` limiter, `config/graphql.php`    |
| `POST /api/v1/login`       | **5 req/min**     | IP                   | inline `throttle:5,1` in `routes/api.php`   |

When a request exceeds the limit you'll get `429 Too Many Requests` with a `Retry-After` header (in seconds). Successful responses include the standard Laravel rate-limit headers `X-RateLimit-Limit` and `X-RateLimit-Remaining`.

Tip: a single `429` from `POST /login` is keyed by IP, so don't spin up a parallel test loop against `/login` from one machine — rotate users via `POST /tokens` once you have an initial token.

## Pagination

List endpoints (those backed by `AnonymousResourceCollection`) return Laravel's standard envelope:

```json
{
  "data":  [ ... ],
  "links": { "first": "...", "last": "...", "prev": null, "next": "..." },
  "meta":  {
    "current_page": 1,
    "from": 1,
    "last_page": 3,
    "path": "...",
    "per_page": 15,
    "to": 15,
    "total": 42
  }
}
```

Two query parameters apply uniformly:

- `per_page` — items per page (default `15`, max **`100`**)
- `page` — page number (1-indexed)

Most list endpoints also expose:

- `search` — free-text search against the most relevant fields
- `sort_by`, `sort_dir` — sort by a whitelisted column, `asc` or `desc` (default `desc`)

Single-item endpoints (`show`, `store`, `update`) return:

```json
{ "message": "...", "data": { ... } }
```

(`message` is omitted for plain `GET show` responses.)

## Error envelope

Every error response is JSON. The shape is consistent across the API:

```json
{
  "message": "Human-readable summary",
  "error":   "machine_readable_code"
}
```

Validation errors additionally include the standard Laravel `errors` map:

```json
{
  "message": "The given data was invalid.",
  "errors": {
    "email": ["The email field is required."],
    "items.0.product_id": ["The selected product id is invalid."]
  }
}
```

| HTTP status | `error` codes you'll see                                             | When                                                                         |
| ----------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `401`       | `unauthenticated`                                                    | Missing/invalid Bearer token.                                                |
| `403`       | `forbidden`                                                          | Authenticated but lacks required permission.                                 |
| `404`       | `not_found`                                                          | Resource doesn't exist or belongs to another organization. A foreign id in the request **body** is a `422` validation error instead. |
| `422`       | `invalid_state`, `already_processed`, `no_items`, `item_mismatch`, `has_orders`, `missing_recipient`, `insufficient_stock`, `cannot_edit`, `cannot_send`, `cannot_delete`, `cannot_receive`, `cannot_cancel`, `no_items_received`, `has_products`, `cannot_delete_default`, `option_in_use`, `max_options_exceeded`, `duplicate_option`, `invalid_product_type`, `circular_reference`, `no_components`, `invalid_status`, `invalid_data_source`, `invalid_columns` | Domain rule violation (in addition to standard validation errors). |
| `429`       | (no `error` field; see `Retry-After` header)                         | Rate limit exceeded.                                                         |
| `500`       | `query_failed`                                                       | Saved-report execution failure.                                              |

## Code examples

The examples below assume:

```bash
APP_URL="http://localhost"
TOKEN="1|paste-your-token-here"
```

### curl

#### List low-stock products

```bash
curl -G "${APP_URL}/api/v1/products" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Accept: application/json" \
  --data-urlencode "low_stock=1" \
  --data-urlencode "per_page=25"
```

#### Create a product

```bash
curl -X POST "${APP_URL}/api/v1/products" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "sku": "WIDGET-001",
    "name": "Blue Widget",
    "selling_price": 19.99,
    "purchase_price": 8.50,
    "stock": 100,
    "min_stock": 10,
    "tracking_type": "none"
  }'
```

#### Adjust stock

```bash
curl -X POST "${APP_URL}/api/v1/stock-adjustments" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "product_id": 42,
    "quantity": -3,
    "type": "damage",
    "reason": "Dropped pallet",
    "notes": "Shrink-wrap on box 14 was torn."
  }'
```

#### Create an order

```bash
curl -X POST "${APP_URL}/api/v1/orders" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "customer_name": "Acme Corp",
    "customer_email": "ap@acme.example",
    "currency": "USD",
    "items": [
      { "product_id": 42, "quantity": 2 },
      { "product_id": 99, "quantity": 1, "unit_price": 49.95 }
    ]
  }'
```

#### Look up a product by barcode

```bash
curl "${APP_URL}/api/v1/barcode/0123456789012" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Accept: application/json"
```

### PHP (using `Http` facade)

Inventoros itself is a Laravel app, so this is the most natural client style:

```php
use Illuminate\Support\Facades\Http;

$client = Http::baseUrl(config('services.inventoros.url').'/api/v1')
    ->withToken(config('services.inventoros.token'))
    ->acceptJson();

// List products
$products = $client->get('products', [
    'search'   => 'widget',
    'per_page' => 25,
])->throw()->json('data');

// Create an order
$order = $client->post('orders', [
    'customer_name' => 'Acme Corp',
    'currency'      => 'USD',
    'items' => [
        ['product_id' => 42, 'quantity' => 2],
    ],
])->throw()->json('data');

// Adjust stock
Http::baseUrl(config('services.inventoros.url').'/api/v1')
    ->withToken(config('services.inventoros.token'))
    ->acceptJson()
    ->post('stock-adjustments', [
        'product_id' => 42,
        'quantity'   => -3,
        'type'       => 'damage',
        'reason'     => 'Dropped pallet',
    ])
    ->throw();
```

`->throw()` raises on `4xx`/`5xx`; wrap calls in `try { ... } catch (\Illuminate\Http\Client\RequestException $e) { ... }` and inspect `$e->response->json()` to read the error envelope.

### JavaScript (browser / Node `fetch`)

```js
const APP_URL = "http://localhost";
const TOKEN   = "1|paste-your-token-here";

const api = (path, init = {}) =>
  fetch(`${APP_URL}/api/v1${path}`, {
    ...init,
    headers: {
      Accept: "application/json",
      "Content-Type": "application/json",
      Authorization: `Bearer ${TOKEN}`,
      ...(init.headers || {}),
    },
  }).then(async (r) => {
    const body = await r.json().catch(() => ({}));
    if (!r.ok) {
      const err = new Error(body.message || `HTTP ${r.status}`);
      err.status = r.status;
      err.body = body;
      throw err;
    }
    return body;
  });

// List products
const { data: products } = await api("/products?low_stock=1&per_page=25");

// Create an order
const { data: order } = await api("/orders", {
  method: "POST",
  body: JSON.stringify({
    customer_name: "Acme Corp",
    currency: "USD",
    items: [{ product_id: 42, quantity: 2 }],
  }),
});

// Adjust stock
await api("/stock-adjustments", {
  method: "POST",
  body: JSON.stringify({
    product_id: 42,
    quantity: -3,
    type: "damage",
    reason: "Dropped pallet",
  }),
});
```

For Vue/Inertia frontends inside Inventoros itself, the same token mechanism works — you can hit `/api/v1` with an `Authorization` header and the user's session will not be used.

## Webhooks

Manage subscriptions with the `/webhooks` endpoints (permission `manage_organization`) or under **Settings > Webhooks**. The HMAC-SHA256 signing secret is returned only by `POST /webhooks` and `POST /webhooks/{id}/regenerate-secret`; store it then. `GET /webhooks/{id}/deliveries` lists recent deliveries with their status and response.

Events are fired by model observers after the database transaction commits, so they fire the same way from the web app, the REST API and GraphQL, and a rolled-back change never fires one.

| Group | Events |
| --- | --- |
| Product | `product.created`, `product.updated`, `product.deleted`, `product.low_stock`, `product.out_of_stock` |
| Order | `order.created`, `order.updated`, `order.status_changed`, `order.approved`, `order.rejected` |
| Payment | `payment.recorded`, `payment.voided` (a refund is a recorded payment of type `refund`) |
| Stock | `stock.adjusted` |
| Purchase order | `purchase_order.created`, `purchase_order.received`, `purchase_order.cancelled` |
| Customer | `customer.created`, `customer.updated`, `customer.deleted` |
| Return | `return.created`, `return.received` |
| Stock transfer | `transfer.created`, `transfer.completed` |
| Work order | `work_order.completed` |
| Stock audit | `stock_audit.completed` |

## GraphQL

`POST /graphql` (Sanctum bearer token, same 60/min limiter as REST).

Queries: `products`, `product`, `orders`, `order`, `suppliers`, `supplier`, `purchaseOrders`, `purchaseOrder`, `stockAdjustments`, `locations`, `categories`, `customers`, `customer`, `returnOrders`, `returnOrder`, `stockTransfers`, `stockTransfer`, `users`, `user` (read-only) and `productVariants`.

Mutations: `createProduct`, `updateProduct`, `deleteProduct`, `createOrder`, `updateOrder`, `createStockAdjustment`, `createSupplier`, `updateSupplier`, `createCustomer`, `updateCustomer`, `createReturnOrder`, `approveReturnOrder`, `receiveReturnOrder`, `createStockTransfer`, `completeStockTransfer`, `createPurchaseOrder`, `updatePurchaseOrder` and `receivePurchaseOrder`.

Every field is gated like the matching REST route: the user must hold the permission and the token must allow it, so a scoped token is enforced the same way over GraphQL. Mutations call the same services as the web app and REST API, so a return received or a transfer completed over GraphQL restocks and moves bins exactly as it would anywhere else. List queries accept `limit` (default 50, max 100). The endpoint shares the REST rate limit of 60 requests per minute.

```bash
curl -X POST "${APP_URL}/graphql" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"query":"{ stockTransfers(status: \"pending\") { transfer_number from_location { name } to_location { name } items { quantity product { sku } } } }"}'
```

## Versioning

The current API is `v1`, served at `/api/v1`. Future incompatible changes will be released under `/api/v2`; `v1` will continue to receive non-breaking additions.
