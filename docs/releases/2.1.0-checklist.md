# 2.1.0 release and deployment checklist

This checklist is a preparation artifact. Check items against the exact commit
and deployment being released; CI results from an earlier head are not evidence
for a later one. No production operation has been performed by adding this file.

## Candidate

- [ ] Merge the reviewed feature stack in order: variance review, large audit
  paging, variant replenishment, then release preparation. Retarget dependent
  PRs after their base merges and verify the final diffs.
- [ ] Check all required CI jobs on the final main commit: SQLite, MySQL,
  PostgreSQL, JavaScript, browser, production dependency install, dependency
  audit, Docker build/smoke and cPanel package build/verification.
- [ ] Confirm `VERSION` and the release notes match 2.1.0; update the pending
  release date in the changelog and remove preparation wording when publishing.
- [ ] Review the lockfile audit and any outstanding dependency alerts against
  the actual locked versions; document unresolved applicable findings.
- [ ] Build the installed plugins' assets, and verify plugin compatibility in
  staging. Core and separately distributed plugin releases are versioned apart.

## Staging upgrade

- [ ] Restore a recent database and file backup into staging; record a few stock
  totals, variant/bin balances, open transfers, POs and audit counts before upgrade.
- [ ] Confirm backup recovery works. Preserve `.env`, `APP_KEY`, uploads and
  installed plugins alongside the database snapshot.
- [ ] Pause inventory integrations and stop or drain writers and queue workers.
  Put the application in maintenance mode using the deployment's normal process.
- [ ] Install the candidate artifact, clear old caches, review migration preview,
  apply migrations, and rebuild caches. For source builds, install lockfiles and
  compile assets; do not run dependency updates on the server.
- [ ] Compare recorded stock totals and open workflow states after migrations.
  Confirm old accepted counts, archived product labels and audit history remain
  readable. Existing audits should not acquire a new approval requirement.
- [ ] Count and recount a staging audit, request a recount, approve a fresh
  variance and complete it. Verify the selected bin and ledger evidence.
- [ ] Exercise a multi-page audit: scan a line off-page, save an offline draft,
  navigate to another page and sync. Check whole-audit completion totals.
- [ ] Configure a manual replenishment rule, create a draft, repeat the request,
  and receive part of its variant line. Confirm the destination bin, outstanding
  inbound quantity, permissions and currency. Enable automation only if wanted.
- [ ] If external uploads are enabled, run Settings > File storage > Check
  connection, upload/download a staging file, and open a retained local upload.
- [ ] Check an existing PO, invoice PDF, plugin page and organization switch with
  an administrator and a user assigned to a single warehouse.
- [ ] Run scheduler and queue smoke checks, restart long-lived workers and verify
  jobs execute. Ensure the dedicated reset queue can be drained; a reset itself
  should only be exercised against disposable staging inventory.

## Publish and production

- [ ] After candidate and staging checks pass, create the approved version tag
  from main. Verify signed cPanel artifacts and the pinned Docker image produced
  by tag workflows before distributing them.
- [ ] Perform the production backup and maintenance window using the same tested
  upgrade process. Keep the previous artifact and pre-upgrade database/files for
  recovery; restore them together if rollback is needed.
- [ ] Check login, assets, stock totals, one warehouse-scoped page, storage and
  worker/scheduler health. Review failed jobs and application logs.
- [ ] Reopen writers and resume integrations, then monitor inventory changes and
  queued work. Record the deployed commit, artifact and completion time.
